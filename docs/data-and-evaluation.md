# Data and evaluation method

The author-created `scripts/build_synthetic_data.py` records eight troubleshooting families, two distinct diagnostic guide snippets per family, and eight ticket phrasings per family. It writes 40 train tickets (indices 0–4), eight validation tickets (index 5), 16 test tickets (indices 6–7), and query labels for the held-out splits. `group_id` and `id` identify each unique ticket. The script uses a fixed ordering and no randomness; `seed` records the intended model-training seed. Passage labels award grade 2 to the primary guide and grade 1 to the secondary guide for a family. The test split is a holdout by **ticket wording**, not by incident family or source author.

Both retrieval methods rank the same 16 passages. TF-IDF uses word and bigram features with cosine-normalized vectors. The Sentence Transformer produces normalized dense vectors, with matrix dot product as cosine similarity. Recall@K counts relevant guides found divided by two; Precision@K counts them divided by K; MRR@K uses the first relevant rank; nDCG@K discounts grades 2 and 1 by rank. Evaluate validation when developing; report test only after choices are fixed. The small, easy corpus may have ceiling effects; compare failures as well as averages.

Generation uses a consistent instruction to emit `CATEGORY`, `FIRST_CHECK`, and a short `RATIONALE`. The base and LoRA variants use the same prompt. The prompted baseline adds one train example. Exact category and first-check accuracy and macro F1 are deliberately strict: missing or malformed fields fail. Rationale quality, unjustified certainty, and unsafe recommendations need human review using the blank fields in each generated record. The training objective is completion-only next-token prediction; instruction tokens have `-100` loss labels. The validation split supplies loss monitoring, not gradients. Generation comparison reads the test split only when explicitly invoked.

On-demand inference records input/output token counts, elapsed generation seconds, output tokens per second and CUDA peak allocated bytes if applicable. Those values depend on model warmup, hardware, batching, and cache state; this code does not run a standardized throughput benchmark. The model size is documented through upstream cards and trainable parameter counts in the training manifest. For stronger measurement later, add fixed warmup, repeated timed runs and CPU/GPU memory tracking; only cite measurements you actually perform.

There are no performance or quality numbers in this release. A possible learning question is whether LoRA improves structured triage on held-out phrasings over the same unadapted base prompt, while keeping a prompted baseline in view. The project does not assert that result in advance.
